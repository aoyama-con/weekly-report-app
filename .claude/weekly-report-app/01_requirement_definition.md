# 新人OJT週報自動生成システム 要件定義書

**バージョン**: 1.0
**作成日**: 2026-01-03
**対象フェーズ**: MVP

---

## 1. プロジェクト概要

### 1.1 背景と課題
- 新人社員の週報作成に時間がかかり、本来の業務時間を圧迫している
- 委託現場ごとに指導方針や報告書の規範が異なり、評価基準がブレる
- 週報の品質が個人差でバラつき、管理側が読みにくく状況把握に時間がかかる

### 1.2 目的（成果指標）
1. **週報作成工数を1/3以下に削減**（箇条書き入力→AI生成→軽微修正のみ）
2. **評価観点・フォーマットの統一**で現場差による評価のブレを解消
3. **管理者が短時間で状況把握できる読みやすい週報**を実現
4. **OJT実施者/新人双方に次週の改善アクション**をAIアドバイスで提供

### 1.3 対象ユーザー（ロール定義）
| ロール | 主な利用機能 |
|--------|--------------|
| **新入社員** | 週報作成（箇条書き入力）、生成、編集、提出、アドバイス閲覧 |
| **OJT実施者** | 週報レビュー、評価入力、アドバイス閲覧、指導計画確認 |
| **管理者（人事/PM/上長）** | 全週報閲覧、フィルタ検索、PDF出力、現場プロフィール管理、ユーザー管理 |

## 2. スコープ定義

### 2.1 MVP（必須機能）
- ✅ ログイン・認証（役割ベース）

## 3. 業務ルール・標準化方針

### 3.1 週報フォーマット
- MVP段階では固定テンプレート（管理画面での編集はPhase2）
- 必須セクション：
  1. 今週やったこと
  2. 学んだこと/気づき
  3. 困ったこと/課題
  4. 来週やること
  5. 相談したいこと

### 3.2 現場差異の扱い
- **現場プロフィール**として登録（現場名、求める姿勢、注意点、機密用語リスト）
- 評価基準（ルーブリック）は現場に関わらず統一
- 生成時に現場プロフィールを参照し、文脈に反映

### 3.3 トーン別生成ルール
| トーン | 文体 | 固有名詞 | 内部課題の扱い |
|--------|------|----------|----------------|
| **社内向け** | 率直・具体的 | 可（権限内） | 明示OK |
| **客先向け** | 丁寧・前向き | 原則マスク | 一般化・前向き表現に変換 |

### 3.4 評価ルーブリック（標準）
| 項目 | 評価観点 |
|------|----------|
| 業務理解 | タスクの目的・背景を正しく理解しているか |
| 主体性 | 自ら考え行動する姿勢があるか |
| 報連相 | 適切なタイミング・粒度で報告・相談できるか |
| 品質意識 | 成果物の精度・レビュー対応の姿勢 |
| 学習姿勢 | 振り返り・改善の意識があるか |
| チーム連携 | 周囲と協力し円滑にコミュニケーションできるか |

各項目：1〜5点 + コメント（任意）

## 4. 機能要件

### 4.1 週報作成（新入社員）

#### 入力項目
- 対象週（自動選択可）
- 現場（選択）
- 今週やったこと（箇条書きテキスト）
- 学んだこと/気づき
- 困ったこと/課題
- 来週やること
- 相談したいこと

#### 処理フロー
1. 箇条書き入力
2. 「生成」ボタン押下
3. トーン選択（社内向け/客先向け）
4. LLMが報告書文体に変換（10〜20秒以内目標）
5. 生成結果を画面表示（編集可能）
6. 保存（draft）または提出（submitted）

#### バリデーション
- 必須項目：対象週、現場、「今週やったこと」最低1項目
- 提出前確認：「生成済みか」「各セクション空欄チェック」

### 4.2 週報閲覧・検索

#### フィルタ条件
- 期間（開始週〜終了週）
- 社員名
- 現場
- ステータス（draft/submitted/reviewed）

#### 表示項目（一覧）
- 社員名
- 対象週
- 現場
- ステータス
- 提出日時
- レビュー状況

#### 詳細画面
- 週報本文（社内向け/客先向け切替表示）
- 評価（あれば）
- アドバイス（あれば）
- PDF出力ボタン

### 4.3 評価・レビュー（OJT実施者）

#### 評価入力
- ルーブリック6項目×5段階評価
- 各項目コメント（任意）
- 総評コメント（任意）
- 保存で週報ステータスを`reviewed`に変更

#### 権限
- 自分が担当する現場の新人のみ評価可能
- 管理者は全て閲覧可能だが編集は不可（運用次第で変更可）

### 4.4 AIアドバイス生成

#### 新人向けアドバイス
- 次週の改善ToDo（3〜5個）
- 優先度（高/中/低）
- 具体的アクション例

#### OJT向けアドバイス
- 褒める点（強み）
- 改善が必要な点
- 次週の指導ポイント

#### 生成タイミング
- OJTがレビュー保存時に自動生成（非同期可）
- または手動で「アドバイス生成」ボタン

#### ガードレール
- 断定的表現・人格否定の禁止
- 医療/法務/ハラスメント判定など高リスク領域は回避
- 不確実な場合は「質問を促す」出力

### 4.5 PDF出力

#### 出力内容
- タイトル（社員名、対象週）
- 週報本文（トーン選択：社内/客先）
- 評価（ルーブリック+コメント）
- AIアドバイス（新人向け/OJT向け）
- 監査情報（作成日、提出日、生成モデル）

#### 要件
- 日本語フォント対応（文字化け防止）
- シンプルなレイアウト（会社ロゴは任意で追加可）
- ファイル名：`週報_{社員名}_{YYYY-MM-DD}.pdf`

### 4.6 管理画面

#### ユーザー管理
- ユーザー一覧（名前、メール、ロール、有効/無効）
- 新規招待（メール送付）
- ロール変更（新人/OJT/管理者）
- 無効化（削除ではなく論理削除）

#### 現場プロフィール管理
- 現場一覧
- 新規作成/編集
- 設定項目：
  - 現場名
  - プロフィールテキスト（求める姿勢、注意点）
  - マスキングポリシー（機密用語リスト、例：案件名→「プロジェクト」）

#### ルーブリック管理
- MVP: 固定（編集不可）
- Phase2: 項目追加・削除・並び替え

### 4.7 監査ログ

#### 記録対象操作
- ログイン/ログアウト
- 週報生成（入力データ、使用モデル、生成時刻）
- 週報編集（差分）
- 週報提出
- レビュー保存
- アドバイス生成
- PDF出力
- 現場プロフィール変更
- ユーザー招待/無効化

#### 保存項目
- 操作日時
- 操作者（User ID）
- アクション種別
- 対象（Report ID / User ID など）
- メタデータ（JSON：入力内容、生成モデル、差分など）

## 5. 非機能要件

### 5.1 セキュリティ

#### 認証・認可
- **認証**: メール/パスワード（最低8文字、英数記号混在推奨）
- **RBAC**: 新人/OJT/管理者の3ロール
- **セッション管理**: トークン有効期限24時間、リフレッシュトークン対応

#### データ保護
- **通信暗号化**: HTTPS必須（TLS 1.2以上）
- **保存時暗号化**: パスワードはbcrypt/argon2、機密フィールドは必要に応じてAES-256
- **プロンプトインジェクション対策**:
  - 入力のサニタイズ（HTML/スクリプトタグ除去）
  - システムプロンプト固定（ユーザー入力と明確に分離）
  - 出力検査（不適切表現・機密情報漏れチェック）

#### マスキング（客先向け出力）
- **二段階チェック**:
  1. 正規表現で固有名詞候補を検出（人名、案件名、システム名など）
  2. LLMで文脈判定し置換（例：案件名→「プロジェクト」）
- **検出ログ**: マスクした用語を監査ログに記録

### 5.2 可用性
- **稼働時間**: 平日 8:00〜20:00（週報作成・提出のピーク時間帯）
- **SLA**: MVP段階は99%を目標（ダウンタイム許容）
- **復旧**: 障害時の復旧手順書を用意（DB復元、ロールバック）

### 5.3 性能
- **週報生成**: 10〜20秒以内（LLM APIのレスポンスタイム次第）
- **超過時の対応**: 再試行ボタン、または非同期キュー＋通知
- **同時利用**: MVP想定50ユーザー（新人30、OJT15、管理者5）
- **ページ表示**: 一覧・詳細とも2秒以内

### 5.4 保守性
- **設定の外部化**:
  - プロンプトテンプレート（JSON/YAMLファイル）
  - ルーブリック項目（設定ファイル、Phase2でDB化）
  - 現場プロフィール（DB）
- **バージョン管理**: 生成に使用したLLMモデル・バージョンを記録
- **ログレベル**: 本番はINFO以上、開発はDEBUG

### 5.5 拡張性
- **Phase2への移行**:
  - 音声入力（別APIエンドポイント追加）
  - テンプレ管理（CRUD API追加）
  - 通知連携（Webhook/メール送信キュー）
  - ダッシュボード（集計API、グラフライブラリ）

## 6. データモデル（論理設計）

### 6.1 テーブル定義

#### User（ユーザー）
| カラム | 型 | 説明 |
|--------|-----|------|
| id | UUID/BIGINT | PK |
| name | VARCHAR(100) | 氏名 |
| email | VARCHAR(255) | メールアドレス（ユニーク） |
| password_hash | VARCHAR(255) | ハッシュ化パスワード |
| role | ENUM('trainee','ojt','admin') | ロール |
| active | BOOLEAN | 有効/無効 |
| created_at | TIMESTAMP | 作成日時 |
| updated_at | TIMESTAMP | 更新日時 |

#### Site（現場）
| カラム | 型 | 説明 |
|--------|-----|------|
| id | UUID/BIGINT | PK |
| name | VARCHAR(100) | 現場名 |
| profile_text | TEXT | 現場プロフィール |
| masking_policy_json | JSON | マスキングルール（用語リスト） |
| created_at | TIMESTAMP | 作成日時 |
| updated_at | TIMESTAMP | 更新日時 |

#### WeeklyReport（週報）
| カラム | 型 | 説明 |
|--------|-----|------|
| id | UUID/BIGINT | PK |
| user_id | FK(User) | 新人社員 |
| site_id | FK(Site) | 現場 |
| week_start | DATE | 対象週の開始日（月曜） |
| status | ENUM('draft','submitted','reviewed') | ステータス |
| input_bullets_json | JSON | 入力された箇条書き（元データ） |
| generated_internal_json | JSON | 生成された社内向け週報 |
| generated_client_json | JSON | 生成された客先向け週報 |
| edited_body_internal | TEXT | 編集後の社内向け本文 |
| edited_body_client | TEXT | 編集後の客先向け本文 |
| submitted_at | TIMESTAMP | 提出日時 |
| created_at | TIMESTAMP | 作成日時 |
| updated_at | TIMESTAMP | 更新日時 |

#### Review（評価）
| カラム | 型 | 説明 |
|--------|-----|------|
| id | UUID/BIGINT | PK |
| report_id | FK(WeeklyReport) | 週報 |
| reviewer_user_id | FK(User) | OJT実施者 |
| rubric_scores_json | JSON | ルーブリック評価（項目:点数:コメント） |
| summary_comment | TEXT | 総評 |
| created_at | TIMESTAMP | 作成日時 |
| updated_at | TIMESTAMP | 更新日時 |

#### Advice（AIアドバイス）
| カラム | 型 | 説明 |
|--------|-----|------|
| id | UUID/BIGINT | PK |
| report_id | FK(WeeklyReport) | 週報 |
| for_role | ENUM('trainee','ojt') | 対象ロール |
| advice_json | JSON | アドバイス内容（構造化） |
| model_version | VARCHAR(50) | 使用LLMモデル |
| created_at | TIMESTAMP | 生成日時 |

#### AuditLog（監査ログ）
| カラム | 型 | 説明 |
|--------|-----|------|
| id | BIGINT | PK（自動採番） |
| actor_user_id | FK(User) | 操作者 |
| action | VARCHAR(50) | アクション種別 |
| target_type | VARCHAR(50) | 対象（Report/User/Site） |
| target_id | VARCHAR(255) | 対象ID |
| meta_json | JSON | メタデータ（詳細） |
| created_at | TIMESTAMP | 操作日時 |


## 7. API設計（高レベル）

### 7.1 認証
- `POST /api/auth/login` - ログイン（email, password → token）
- `POST /api/auth/logout` - ログアウト
- `POST /api/auth/refresh` - トークンリフレッシュ

### 7.2 週報
- `GET /api/reports` - 週報一覧（フィルタ: user_id, site_id, week_start, status）
- `GET /api/reports/:id` - 週報詳細
- `POST /api/reports` - 週報作成（draft）
- `PUT /api/reports/:id` - 週報編集
- `POST /api/reports/:id/generate` - LLM生成（body: tone='internal'|'client'）
- `POST /api/reports/:id/submit` - 提出
- `GET /api/reports/:id/pdf` - PDF出力（query: tone）

### 7.3 レビュー
- `POST /api/reports/:id/review` - 評価保存（rubric_scores_json, summary）
- `GET /api/reports/:id/review` - 評価取得

### 7.4 アドバイス
- `POST /api/reports/:id/advice` - アドバイス生成（非同期可）
- `GET /api/reports/:id/advice` - アドバイス取得

### 7.5 管理
- `GET /api/admin/users` - ユーザー一覧
- `POST /api/admin/users` - ユーザー招待
- `PUT /api/admin/users/:id` - ロール変更・無効化
- `GET /api/admin/sites` - 現場一覧
- `POST /api/admin/sites` - 現場作成
- `PUT /api/admin/sites/:id` - 現場更新

### 7.6 監査
- `GET /api/admin/audit-logs` - 監査ログ一覧（フィルタ: actor, action, date_range）

**備考**: 非同期処理（LLM生成、PDF生成）はジョブキューを使い、完了時に通知またはポーリングで結果取得を想定。

- メールアドレス、パスワード入力
- ログインボタン
- パスワードリセット（Phase2）

- **ヘッダー**: ユーザー名、ロール表示、ログアウトボタン

- **OJT**: 担当新人の週報一覧（レビュー待ち優先表示）

- 対象週（日付ピッカー、デフォルト今週）

- 入力フォーム（各セクション複数行テキストエリア）

- 「下書き保存」「提出」ボタン

#### (4) 週報詳細画面

- 週報本文（読み取り専用 or 編集モード切替）
- 評価セクション（あれば表示）
- アドバイスセクション（新人向け/OJT向け）

- ルーブリック評価フォーム（6項目×5段階スライダー+コメント）

#### (6) 管理画面
- **ユーザー管理**タブ: 一覧、招待、ロール変更、無効化
- **現場管理**タブ: 一覧、新規作成、編集（プロフィール、マスキング用語）

| リスク | 対策 |
|--------|------|
| **誤生成・品質低下** | 編集可能UI、再生成ボタン、差分表示、テンプレ固定 |
| **情報漏えい（機密流出）** | RBAC、マスキング（正規表現+LLM）、監査ログ、LLM送信データ最小化 |
| **プロンプトインジェクション** | 入力サニタイズ、システムプロンプト固定、出力検査 |
| **運用負荷（管理者疲弊）** | 現場プロフィール最小項目、テンプレ固定、管理画面簡素化 |
| **LLM API障害** | タイムアウト設定、再試行、キュー、障害時の手動入力フォールバック |
| **評価の不公平感** | ルーブリック明示、評価理由コメント必須化（運用ルール） |

## 11. 受け入れ条件（Acceptance Criteria）

1. 箇条書き入力から、社内向け/客先向けの週報が生成できる
2. 客先向けでは固有名詞・内部事情が自動マスクされ、検出ログが残る
3. 生成文章はユーザーが編集でき、提出後にレビューが紐づく
4. 評価が標準ルーブリック（6項目×5段階）で入力でき、AIアドバイスが新人/OJT双方に表示される
5. 週報一式（本文+評価+アドバイス）がPDF出力でき、日本語が崩れない
6. 主要操作（生成、提出、レビュー、PDF出力）が監査ログに記録される
7. 管理者が期間/社員/現場/ステータスでフィルタ検索できる
8. OJTは自分の担当現場の新人の週報のみ編集できる（RBAC）

## 14. 付録

### 用語集
- **週報**: 新人が週次で作成する業務報告書
- **ルーブリック**: 評価基準を明文化した表（項目×観点）
- **トーン**: 文体・語調（社内向け=率直、客先向け=丁寧）
- **マスキング**: 固有名詞や機密情報を一般表現に置換する処理
- **RBAC**: Role-Based Access Control（役割ベースアクセス制御）
